# LARGE_CHANGE.md

影響範囲の大きい変更を行うときに使う。

通常の実装より先に、
「どこまで変わるか」「どう壊れるか」「どう戻せるか」を確認する。


# 1. Scope

変更対象と影響範囲を確認する。

- どの機能・構造が変わるか
- 何が影響を受けるか
- 変更しない部分はどこか
- 既存データや設定に影響するか


# 2. Current Structure

必要に応じて以下を参照する。

- 現在の状態 → `../PRODUCT_CURRENT_STATE.md`
- 技術構造 → `../ARCHITECTURE.md`
- 最近の作業 → `../WORKLOG.md`

現在の構造を確認してから変更方法を決める。


# 3. Connection Check

将来の接続可能性へ影響する場合は
`../CONNECTION_POSSIBILITY_CHECKLIST.md` を確認する。

将来機能を先行実装せず、
現在の変更で選択肢を不必要に潰さない。


# 4. Verification Plan

変更前に、どこまで検証する必要があるか決める。

`../VERIFY.md` から必要な検証方法を選ぶ。

通常変更より広い範囲の回帰確認が必要か検討する。


# 5. Split

可能なら変更を安全な単位へ分割する。

一度に全部変更する必要がない場合は、
途中で検証できる境界を作る。

大規模な未コミット変更が増えすぎる場合は、
安全な地点でHumanへコミットを提案する。


# 6. Implement

段階ごとに変更し、
各段階で前提が崩れていないか確認する。

計画より実際の観測結果を優先する。


# 7. Verify

変更対象だけでなく、
影響を受ける周辺も確認する。

問題が見つかった場合は
必要に応じて `BUG_FIX.md` を使う。


# Output

完了時には最低限、以下が分かる状態にする。

- 何を大きく変更したか
- どこまで影響したか
- どう検証したか
- 既存機能への影響を確認できたか
- 残っているリスクやHuman確認があるか
