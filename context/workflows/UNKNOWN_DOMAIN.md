# UNKNOWN_DOMAIN.md

未知・専門外・経験の少ない領域を扱うときに使う。

「実装できそう」だけで進まず、
まず調査・観測・検証できる範囲を確認する。


# 1. Identify

何が未知なのかを具体的に切り分ける。

問題全体を「未知」とせず、
既知の部分と未知の部分を分離する。


# 2. Research

実装より先に必要な情報を調べる。

優先して確認する。

- 公式ドキュメントや一次情報
- 既存の標準的な解決方法
- 利用可能なライブラリ・ツール
- 既知の制約や失敗例

分からない部分を推測で埋めない。


# 3. Observability

その領域をAI自身が観測・検証できるか確認する。

- 結果を直接確認できるか
- 成功 / 失敗を判定できるか
- 問題発生時に原因を切り分けられるか
- 利用可能な検証手段があるか

既存の検証方法は `VERIFY.md` を確認する。

外部サイト・APIの挙動（bot対策、レート制限、レスポンス形式など）は、
ドキュメントや類似実装からの推測だけで進めず、
実装前に最小限のリクエスト（例: curlで直接叩く）で直接確認する。


# 4. Reduce Unknowns

未知領域そのものを小さくできないか検討する。

- 既製手段へ任せる
- 既知の技術へ置き換える
- 未知部分を隔離する
- Humanが判断できる境界まで縮小する

すべてを自分たちで扱うことを前提にしない。


# 5. Decide

調査結果をもとに、以下のいずれかを選ぶ。

**Proceed**
十分に理解・観測・検証できるため進める。

**Experiment**
小さく安全に試せるため、限定的に実験する。

**Delegate**
既製ツール・外部サービス・別の専門手段へ任せる。

**Defer**
現時点では扱わず保留する。

**Abandon**
安全または確実に扱えないため諦める。


# 6. Explain

未知領域を採用する場合はHumanへ、

- 何を使うのか
- 何を担当するのか
- なぜ採用できると判断したのか
- どこまで自分たちで確認できるのか

を非エンジニア向けに簡潔に説明する。


# Output

完了時には最低限、以下が分かる状態にする。

- 何が未知だったか
- 調査して何が分かったか
- どう観測・検証できるか
- Proceed / Experiment / Delegate / Defer / Abandon のどれを選んだか
