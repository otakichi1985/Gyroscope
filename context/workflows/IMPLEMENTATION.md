# IMPLEMENTATION.md

通常の新機能・機能変更を実装するときに使う。

必要以上に大きく作らず、
検証可能な単位で実装を進める。


# 1. Understand

実装する目的と範囲を確認する。

必要に応じて以下を参照する。

- 現在の状態 → `../PRODUCT_CURRENT_STATE.md`
- 技術構造 → `../ARCHITECTURE.md`
- 最近の作業 → `../WORKLOG.md`

目的や要件自体がまだ曖昧なら、
実装せず `DISCOVERY.md` へ戻る。

変更対象のUI要素や表示場所が曖昧な依頼
（「◯◯の可視性を上げる」「◯◯を見やすく」など）は、
解釈を決め打ちせず、対象要素をHumanへ確認してから実装する。


# 2. Inspect

変更する前に、関係する既存実装を確認する。

- どこを変更するか
- 何に影響するか
- 既存の仕組みを再利用できるか

コードを読む前から実装方法を決めつけない。

## Structure and Locality

初期実装の段階から、機能と責務を基準にコードを適切な単位へ分ける。
単純にファイルを小さくするのではなく、変更要求を受けたときにディレクトリ名・ファイル名から変更対象を推測でき、必要な領域だけを読める構造を目指す。

- 同じ理由で理解・変更されるコードは近くに置く。
- 異なる理由で変更される責務は可能な限り分ける。
- `utils`、`helpers`、`misc`、`manager` など、内容を読まないと役割が分からない曖昧な分類へ安易に集約しない。
- 親ディレクトリとの組み合わせで責務が明確なら、ファイル名で同じ情報を重複させない。
- 責務を簡潔な名前で説明できない場合は、複数の責務が混在していないか確認する。

分割によって関連コードの移動・探索が増える場合は、分割しすぎと判断する。


# 3. Design

今回必要な範囲で実装方法を決める。

実装前に、変更対象の責務境界と配置を確認する。
まずproject contextとディレクトリ構造から対象を推定し、理由なくリポジトリ全体を読まない。
初期範囲で不足していることが分かった場合にのみ、依存先・呼び出し元・隣接モジュールへ探索を広げる。

新しい技術や未知領域が必要なら
`UNKNOWN_DOMAIN.md` を参照する。

将来の接続可能性へ影響しそうな変更なら
`../CONNECTION_POSSIBILITY_CHECKLIST.md` を確認する。

将来のためだけの機能や抽象化は追加しない。


# 4. Prepare Verification

実装前に、結果をどう確認するか決める。

利用可能な検証方法は `../VERIFY.md` から選ぶ。

十分な観測手段がない場合は、
実装を進める前に観測方法の追加・改善を検討する。


# 5. Implement

検証可能な単位で小さく実装する。

既存の正常な部分まで不用意に変更しない。

途中で前提が崩れた場合は、
当初の計画に固執せず必要な工程へ戻る。


# 6. Verify

`../VERIFY.md` の適切な方法を使って結果を確認する。

問題が見つかった場合は、
推測修正を繰り返さず原因を観測する。

必要なら `BUG_FIX.md` へ切り替える。


# Output

完了時には最低限、以下が分かる状態にする。

- 何を実装したか
- 目的を満たしているか
- どう検証したか
- 残っている問題があるか
