## v1: アプリ内オーバーレイ方式（撤回済み）

設定画面から起動する、アプリのウィンドウ内にオーバーレイ表示するクリック選択式の
編集モード。要素をクリックして選択→インラインstyleでプロパティを調整。

**実機で使ってみて破綻した点（ユーザー指摘）:**
- 小さい要素（アイコン等）をクリックで選びにくい
- 隣接要素が落とす影など、「クリックした要素自身のプロパティではない」効果に
  一切アクセスできない
- `::before`/`::after` 疑似要素はDOMノードではないためクリック対象にならない
- オーバーレイがGUI本体に重なるため、全体の見た目を確認しにくい
- 変更を戻す方向（マイナス方向の調整）ができない項目があった

## v2: 別ウィンドウ＋「3つの探し方」方式

上記の反省を受けて設計し直した:
- 編集UIをアプリ本体とは別のOSウィンドウ（`editor.html`、Tauriの2つ目の
  ウィンドウ）に分離。`BroadcastChannel`で本体側（agent）と編集ウィンドウ間を通信
  （Tauri IPCではなく、同一オリジンのウィンドウ間通信で完結させ、capabilities変更を
  避けた）
- クリック選択一本槍をやめ、3つの入口に分けた:
  1. **場所から** — カーソル位置に `document.elementsFromPoint` を使い、
     重なっている要素をz-order順に一覧表示（クリック選択の代替、小さい要素にも
     強い）
  2. **効果から** — 「影/背景/文字色/枠線/角丸/余白/ぼかし」等のカテゴリを選ぶと、
     アプリ全体をスキャンして実際にその効果を持つ要素（疑似要素含む）を一覧表示
  3. **構造から** — 手動でキュレーションした画面構造ツリー（`gyroscopeManifest.ts`
     の `SCREEN_MAP`）から選ぶ
- インスペクタ（選択中要素のプロパティ一覧・プリセットボタン・変更履歴）、
  スキン配色エディタ、状態プリセット切り替え（読み込み中/空/エラー）も実装

このv2の基本部分（3つの探し方＋インスペクタ）は実機で動作確認済みだったが、
**要件そのものを見直すため、今回すべて撤回した**（後述）。

### 踏んだ重大なバグ：同期コマンドから`.build()`を呼ぶとハングする

編集ウィンドウを開く `open_editor_window` コマンドで、白い空白ウィンドウ→
最終的にはOS全体が固まりかけるレベルの症状に遭遇した（過去のトレイ関連の
システムハング事例と類似の症状だったため、ユーザーが即座に気づいて報告し、
作業を一旦止めて安全確認してから再開した）。

原因の特定に至った過程:
1. `WebviewUrl::External` に変えてみる → 効果なし
2. `app.run_on_main_thread(...)` で `.build()` を包む → 症状が変化しただけで解決せず
   （`eprintln!` 計測で `.build()` 直前は毎回実行されるが直後が永久に実行されない
   ことを確認）
3. `run_on_main_thread` を外して直接 `.build()` を呼ぶ → 症状は同じ
4. **最終的な修正: コマンド関数を `fn` から `async fn` に変えるだけで即解決。**
   推定原因: 同期コマンドはWebView2からのIPCコールバック自体の中で（呼び出し元の
   ネイティブコールスタックに入れ子のまま）実行されており、WebView2自身の
   コントローラ生成が非同期でイベントループの継続を必要とするため、そのスタックの
   中から呼ぶと自己再入でデッドロックする

**教訓（一般的なTauri Windows開発の知見、ツール自体の存否とは無関係に価値がある）:
新しくウィンドウを作る／ネイティブ描画APIに触るコマンドは必ず `async fn` にする
こと。** 中身に `.await` が無くても、`async` を付けるだけでTokio側にスケジュールされ
呼び出し元のコールスタックから外れるため問題が起きなくなる。撤回に伴い
`CLAUDE.md` の該当エントリも削除したので、再度この種のコマンドを書く際はこの記録を
参照すること。

## 実際に見つかった、まだ直していないCSS不具合

オーディナリー／カーディナリティ両スキンで、記事一覧の一番上のカードの上端に
「影のような帯」が見える（ユーザーが実機スクリーンショットで指摘）。

v2ツールで調査した際、当初「絞り込みバー自体に `box-shadow` が残っている」という
仮説を立てたが、実際にツールで測ると常に「なし」と出て誤りと判明。再調査の結果:

- **絞り込みバーは `.skin-ordinary` の後勝ちルールで `box-shadow: none` に
  明示的に上書きされている**（`index.css` 1068〜1083行付近、
  `.skin-ordinary .app-titlebar, .app-filterbar, .timeline-toolbar { box-shadow:
  none; ... }`）
- **記事カード側には実在する `box-shadow`（接触影）がある**
- カード同士が縦に並んでいる場合は、隣接カードの明るいグロー（`--plate-glow`）が
  互いに打ち消し合って目立たないが、**一番上のカードの上には「打ち消す側」の
  絞り込みバーがそもそも影を持たない**ため、カード側の暗い接触影だけが単独で
  見えてしまう

**つまりこれは単一要素のCSSプロパティの値としては存在しない、2要素の重なりが
作る創発的な効果**。「1要素を選んでプロパティを見る」という設計のツールでは
原理的に見つけられない、とユーザーが指摘した通りだった。

この不具合自体は `BACKLOG.md` の「修正予定」に記録済み（このファイルにも残す形で
補足した）。**まだ修正していない。**

## 「測る」— 4つ目の入口（実装着手・未完のまま撤回）

ユーザーからの指示: 「そこは俺が直接直すなりしたいからツールに入れて。他にもそういう
のがあれば盛り込んでほしい。」— 上記の不具合をきっかけに、実際にレンダリングされた
画面ピクセルを直接計測できる4つ目の探し方をツールに追加する方向で設計・実装に着手した。

### 設計（`.claude/plans/composed-imagining-wall.md` に完全な計画あり）

- アプリのウィンドウ上で矩形をドラッグ選択 → 画面上のその範囲を実際にキャプチャ
  （DOMではなく合成後の本物の画面）→ 編集ウィンドウ側に画像と明るさ/色の実測値を表示
- 「選択中の要素を一時的に隠して測り直す」機能（Before/After比較、
  以前手動でやった「ウィンドウごと隠してピクセル差分を見る」手法の自動化版。
  `verify-transparency-by-pixel-diff.md` の技法をそのまま1要素単位に応用したもの）
- 座標変換は `getCurrentWindow().innerPosition()` + `devicePixelRatio` で
  クライアント座標→画面座標に変換

### 実装済みだった部分（撤回時点、コードは削除済み）

`src-tauri/src/dev_tools.rs` に `capture_screen_region(x, y, width, height) ->
Result<Vec<u8>, String>` を実装し、`cargo check`/`cargo clippy -- -D warnings`
とも通っていた（Rustのバックエンドのみ完成、フロント側は未着手）。実装内容は
素のGDI呼び出し（`GetDC`→`CreateCompatibleDC`→`CreateCompatibleBitmap`→
`BitBlt`→`GetDIBits`、`vibrancy.rs`/`opacity.rs` と同じ「生のWin32を直接叩く」
流儀）。BGRA→RGBA変換込み。`open_editor_window` と同じ理由で `async fn` 必須
（上記のハング教訓）。`lib.rs` の `invoke_handler` にも登録済みだった。

未着手だった部分:
- `src/dev-tools/protocol.ts` への測定系メッセージ型追加
- `DevAgent.tsx` への矩形ドラッグモード実装

  「隠して測り直す」ボタン）
- 「場所から」モードへの素通り装飾要素（`pointer-events: none` の
